A shell for the 21st century.

Unix pipes move text, and every pipeline hides a small parser that breaks silently. meersh passes typed records instead, makes language models ordinary pipeline stages, and checks every action against who wrote it, what it touches and whether it can be undone. Written in Rust, for Linux, local models first.

meersh in three minutes

A narrated tour of the real shell in a made-up project. Watch records flow through pipes, a question mark turn plain words into a pipeline, and a model plan a deletion that waits for your approval and can be undone. Then see the permission model decide what you, a model and a coding agent may do, and the kernel hold a program to the folder you allowed.

Objects, not text

PowerShell showed that a shell can pass objects. meersh does it on Linux, with plain data that survives a pipe, a file or a language model.

Typed records

ls returns fs.entry records with a filesize and a date, ps returns proc records. where size > 10mb needs no parsing, and ps | where cpu > 50 | kill needs no xargs.

Objects with methods

$f.delete(), $f.hash(), $p.ports(). Every object carries its identity, so a stale listing can never hit a different file or a reused pid. help fs.entry lists fields and methods.

Legacy tools become records

Adapters turn ip, ss, systemctl, journalctl, git and more into tables when a builtin reads them. Rust tools can send real objects across the process boundary.

Language models as pipeline stages

A model can write a pipeline, work on data, or act on objects. It never gets more than the role needs, and local models through Ollama are the default.

Transform data

llm map, llm where, llm parse, llm rank, llm group and llm join take a meersh type, turn it into a JSON Schema and return typed values. Rows go in batches, answers are cached, and unsure rows can cascade to a stronger model.

Act on objects

ls | llm "delete all files larger than 5mb" shows the model only the type and its methods, never the files. It writes a pipeline over the input, meersh checks that it can only touch what was piped in, and plans it.

Write pipelines

? the three biggest files here turns a request into a pipeline. The planner sees the request and the types, not the data, so text inside your files cannot steer it. This follows the CaMeL design against prompt injection.

meersh, with qwen3:4b on Ollama
〉ls | llm "delete all files that are larger than 5mb"

  where size > 5mb and type == file | each { $it.delete() }
  # actor wrote this. The instruction asks to delete all files larger than 5mb. The pipeline first filters the table for rows where the size is greater than 5mb and the type is a file. Then, it applies the delete operation to each matching file.

A real run with meersh -c. The model saw table<fs.entry> and its methods, nothing else. Without a terminal to ask, meersh applies nothing. In the shell the same plan waits for your answer, for all rows or only some.

Every action has an author, a target and a right

rm out/demo.o right after creating it is harmless. rm ~/thesis.tex is a disaster. The danger is in the target and in who decided, so that is what meersh checks.

Remove what you created

A ledger records what every session and agent created. A model may change or delete what it created itself and nothing else. Ownership lapses as soon as someone else edits the file.

Plan first, undo later

Anything that writes, deletes or calls a model is planned before it runs. You approve all of it, some rows, or a narrow rule. Every action is journaled with its inverse, and undo takes it back.

Sandboxes and Landlock

sandbox { ^npm install } runs a program in an overlay and shows what it would change. with {fs.write: ./out, net: none} { ^make } lets the kernel enforce the limits.

The shell for your coding agents

meersh mcp gives Claude Code and other agents typed tools instead of a bash prompt. Each agent is its own principal with its own ledger and leases, so several agents in one project cannot delete each other's work. Programs your policy allows run under Landlock, confined to the project. Everything else comes back to the agent as a plan for you to approve. 

claude mcp add --scope user meersh -- ~/.local/bin/meersh mcp --agent claude --unique

The repository has the CLAUDE.md section, the Claude Code permissions and the policy that make an agent use meersh instead of bash, in integrations/claude.

Get started

One command installs meersh on any Linux. For the model features, a local Ollama or a logged in Claude Code is enough.

1. Install

One binary for the shell and one multi call binary for the tools, so they serve bash users with text too. Both are linked statically and run on every distribution on x86_64 and ARM64. The script puts them in ~/.local/bin, or in /usr/local/bin as root. Running it again updates meersh. 

curl -fsSL https://github.com/ribalba/meersh/releases/latest/download/install.sh | sh
Debian, Ubuntu .deb x86_64 .deb ARM64
Fedora, openSUSE .rpm x86_64 .rpm ARM64
Any Linux .tar.gz x86_64 .tar.gz ARM64

Every version and the checksums are on the releases page. To build from source you need a Rust toolchain. Run make install PREFIX=~/.local in a clone of the repository.

2. Pick your models

Without a config meersh uses Ollama on this machine. Claude Code and any OpenAI compatible server are one section of config.toml each. The installer puts an example in ~/.local/share/doc/meersh, the packages in /usr/share/doc/meersh. 

cd ~/.local/share/doc/meersh
cp config.example.toml \
  ~/.config/meersh/config.toml
llm backends

3. Try it

Tab completes commands, flags and the columns of the data flowing in. help is a table like everything else. 

meersh
ps | sort-by cpu -r | first 5
help | where effect == destructive

4. Read the design

CONCEPT.md explains the object model and what meersh takes from Nushell, PowerShell and uutils. AUTHORITY.md explains principals, ownership, plans and models that act on objects.

meersh is the meerkat shell, a sibling of the meerail mail client, the meercal calendar and the meerato todo tool.
